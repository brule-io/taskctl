# Protocol checkpoint after three import paths

Decision date: 2026-09-07. Owning task: `TASK.protocol.checkpoint`.
This checkpoint admits bounded implementation and conformance work. Native v1
remains unfrozen; no repository-wide adoption or service deployment is admitted.

## Evidence and retained model

The reviewed public source is divergent-proof closure commit
`0425fe426c56c85e5752a5b29d9f7dd15daae820`. Fantastikt and Brule exercised actual
consumer adoption; the third path is the independently authored object-record
[specimen](DIVERGENT-IMPORT.md), with exact
[cross-platform evidence](proof/divergent-import/validation.json). The specimen
passed 102 identical JVM/native behavioral identities and 144 process cases on
each supported platform. Its open/closed projection has no unresolved semantic
mismatch. Unsupported source states and execution predicates are rejected.

The existing identity, task DAG, semantic contract, lifecycle/currency split,
revision-aware observations, immutable closure evidence and typed extension
boundary survive this checkpoint. Source formatting, object member order and
optional annotations do not acquire semantic authority. Historical receipts and
imports retain the contracts and dialects they actually describe.

Tasks remain the executable causal nodes. Roadmaps are durable lines of advance;
epics are capability scopes. Membership, association and prerequisite edges are
independent indexes. No hierarchy, exclusive ownership or implicit task dependency
is inferred from planning structure. The nominal identity types and `Value`
algebra remain mandatory; no untyped state or unchecked-cast exception is added.

## Dispositions of the review findings

| Finding | Decision and required proof |
| --- | --- |
| `doctor`, `context` and `snapshot` currently share a large summary | Give each a distinct versioned result contract. Doctor reports diagnostic status and counts; context supplies a deterministically bounded actionable briefing with explicit truncation and follow-up locators; snapshot exports the complete typed ledger view. Context size must be bounded even for large record text. No implicit Git, filesystem writes or probes. `TASK.protocol.read-models` owns implementation and process parity. |
| Planning amendments have no native audit; archival/acceptance are unsettled | Add independent immutable planning revisions and explicit CAS amendments with actor/reason evidence. Adoption records the existing planning baseline without inventing historical amendments. Archival is an explicit planning status and never deletes members or changes task readiness. Acceptance is an explicit assessment of an exact planning scope/revision and observed task contracts/inputs; it is never inferred from every task being closed. Old assessments remain historical after scope/input changes. `TASK.protocol.planning-history` owns the versioned draft, cold reconstruction and task-contract independence proof. |
| Providers are evaluated locally without a persisted effective profile throughout history/currency | Keep the shipped minimal profile as the only activated profile until `TASK.protocol.provider-profile` proves persisted exact profile/provider identities and effective prerequisite observations through the shared reducer, history, file storage and current-input evaluation. New semantic envelopes must preserve the meaning of existing empty-profile contracts. Deterministic providers may contribute validation, edges, readiness blockers and evidence checks, never transitions. Installation alone grants no authority. External probes remain separate explicit evidence-producing operations. |
| Actor time is a nonblank string and could be confused with server time | Preserve legacy timestamp strings and their historical hashes through a distinct typed legacy representation. New assertion envelopes require a validated occurrence timestamp. Authoritative acceptance time belongs to the accepting storage boundary, is separately typed, and cannot be supplied by an actor as authority. Ordering and CAS use revisions, never actor clocks. `TASK.protocol.evidence-time` owns compatibility and invalid-input tests before the remote kernel. |
| Whole-ledger file CAS could dictate remote contention behavior | Retain `Revision` as the identity of a complete snapshot and retain the existing `apply(expectedRevision, transition)` semantics. The kernel first proves strict whole-ledger CAS against file behavior, including concurrent races. Measure unrelated-writer contention and record its limits. Any narrower task-scoped precondition must be a separately typed, explicitly versioned operation with observed-input fencing and conformance, not a silent reinterpretation of `Revision`. `TASK.remote.kernel` owns that experiment. |
| Same schema labels can describe different legacy structures | Require an explicitly selected versioned adapter, exact source revision/content witnesses, structural validation, injective full-identity mapping and manifest-bound review. Do not classify a historical dialect as native v1. The new specimen proves this rule without adding a general runtime adapter loader. |
| Historical closure can coexist with unchecked criteria or missing current observations | Preserve the historical source fact and its classification. It is not current verification, a native receipt or a reason to erase the old closure. Require explicit review in causal order; transitive input changes remain visible after an intermediate review. Existing tests prove this behavior and remain mandatory. |
| Claimed/blocked state, host, operator, deadline and authority restrictions cannot be optional labels | These concepts stay capabilities rather than new universal task states. A proposed adapter must retain source state and restrictions in required typed semantics and prove equivalent readiness/evidence behavior under an available pinned provider. Until that proof exists, such imports and the corresponding consumer adoptions remain blocked. The open/closed specimen does not establish that proof. |

The planning acceptance decision does not require every roadmap to have a finish
line, nor every epic to be closed. A durable lane may remain active indefinitely.
Any new optional acceptance criteria belong to a versioned planning contract; an
assessment binds the scope actually reviewed. Changes to planning alone must not
rewrite task contracts or create causal edges. Active-lane exclusivity, release
gates and execution ownership remain required project capabilities when relevant.

## Admitted work and causal gates

Four correction tasks are admitted after this checkpoint: distinct read models,
planning history, evidence time and persisted provider/profile semantics. Their
wire/storage choices remain explicitly versioned alpha contracts and must include
old-data compatibility tests. `ROADMAP.pre-v1-corrections` projects this work;
membership grants no authority beyond task prerequisites.

The existing public compatibility tasks keep their full identities and original
prerequisite chain. Complex planning conformance additionally waits for planning
history; workspace/environment conformance additionally waits for persisted
provider semantics. Related-ledger and legacy-authority conformance retain their
downstream gates. They use isolated, publishable specimens and do not execute
operational consumer migrations.

The bounded Postgres/HTTP kernel is admitted only after this checkpoint, typed
evidence time and planning history. It must use the shared reducer, prove file
equivalence, transaction/restart behavior, lifecycle events and strict stale-CAS
rejection, and characterize contention. Initial scope is one explicitly selected
ledger and the minimal profile. No tenancy, billing, RBAC, product UI, production
deployment or background operation is included. Provider activation requires its
separate proof even if the kernel otherwise works.

IDL projection still waits for the kernel. The v1-candidate assessment retains
related-ledger/authority and IDL evidence and additionally requires the distinct
read models. Planning, provider and timestamp corrections are also prerequisites
through the strengthened paths. The assessment is a later decision; completing
this checkpoint does not freeze native v1.

## Adoption and implementation limits

The checkpoint admits implementation of the preserving mechanisms and additional
specimens, not migration of a consumer whose required behavior is unsupported.
An owning consumer task must still select an exact source revision, validate its
adapter and required capabilities, retain evidence and prove its integration.
Private source and operational tracking stay with their owners.

The [graph change evidence](proof/protocol-checkpoint/graph-review.json) records
the newly admitted contracts, added prerequisite gates, explicit reviews of
affected plans and the resulting frontier. Existing task prerequisites and all
previously closed evidence are preserved. No history or HEAD object is edited
outside taskctl's CAS transitions.
